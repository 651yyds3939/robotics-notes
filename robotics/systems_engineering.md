# 机器人系统工程与全生命周期质量

> **定位**：本专题回答如何把“各模块分别能运行”提升为“整机在目标场景中可验证、可集成、可维护地运行”。
>
> 核心闭环：**需求与场景 → 架构与接口 → 预算与风险 → 实现与集成 → 验证确认 → 发布运维 → 现场反馈与变更追踪**。
>

## 一、为什么机器人需要系统工程

机器人同时包含机械、电气、嵌入式、通信、感知、规划、控制和 AI 模型。单项指标优秀不代表整机可用，常见失败往往发生在模块边界：

- 消息字段正确，但单位、坐标系或时间戳不一致。
- 平均延迟合格，但偶发抖动导致控制目标过期。
- 仿真策略有效，但 URDF、关节顺序或标定版本与真机不一致。
- 节点能自动重启，但重启后错误地恢复运动。
- 算法成功率很高，但没有定义适用环境、失败处理和验收方法。

因此，系统工程关注的不只是“用了什么技术”，还包括边界、接口、预算、风险、证据、版本和责任人。

## 二、需求工程与运行设计域

### 2.1 先定义运行设计域 (ODD)

运行设计域用于说明机器人在什么条件下承诺能力，至少包括：

| 维度 | 示例 |
|------|------|
| 场地 | 室内/室外、平地/坡道、门宽、台阶高度 |
| 环境 | 光照、温湿度、粉尘、雨水、电磁环境 |
| 人与障碍 | 人群密度、动态障碍、儿童/宠物、协作距离 |
| 任务 | 载荷、速度、精度、连续运行时间、任务频率 |
| 基础设施 | 网络覆盖、定位设施、充电条件、远程运维能力 |

ODD 之外的行为也要定义：拒绝任务、请求人工接管、能力降级或安全停止，而不是让系统在未知条件下继续尝试。

### 2.2 把模糊目标改成可验证需求

| 模糊说法 | 可验证表达示例 |
|----------|----------------|
| 导航稳定 | 在指定地图与人流条件下完成 100 次任务，成功率达到目标值 |
| 控制实时 | 控制周期、P99 抖动、deadline miss 和最大数据年龄满足阈值 |
| 抓取准确 | 在指定物体集、距离和光照下统计成功率与末端位姿误差 |
| 故障可恢复 | 注入指定故障后，在规定时间内进入对应安全状态 |

阈值必须结合具体平台、场景和风险确定，不能把示例数值直接当成通用标准。

### 2.3 需求分解与双向追溯

需求按以下路径逐级分解：

```text
利益相关方需求 → 系统需求 → 子系统需求 → 软件/硬件需求
       ↕             ↕             ↕              ↕
场景验收证据     系统测试       集成测试        单元/台架测试
```

每条关键需求建议记录唯一 ID、来源、负责人、优先级、设计依据、验证方法和通过阈值，并建立：

```text
需求 ↔ 架构模块 ↔ 接口 ↔ 风险 ↔ 测试用例 ↔ 测试报告
```

- **Verification（验证）**：是否按照规格把系统造对。
- **Validation（确认）**：造出的系统是否解决真实用户和场景问题。

## 三、系统架构、职责边界与接口契约

### 3.1 职责边界

明确感知、估计、任务、规划、控制、驱动和安全模块的输入、输出、所有者与禁止职责：

- 感知节点输出观测或目标，不直接绕过控制器下发力矩。
- 任务层下发带时效的意图，不阻塞实时控制环。
- 安全链能独立否决运动指令，业务节点不能覆盖硬件急停。
- 同一执行资源只能有一个最终控制权仲裁点，避免多节点争抢。

### 3.2 数据接口契约

ROS Topic、Service、Action、共享内存或现场总线接口都应明确：

| 类别 | 必须说明的内容 |
|------|----------------|
| 数据 | 类型、字段语义、单位、精度、合法范围 |
| 时空 | 坐标系、时间戳来源、同步误差、数据有效期 |
| 性能 | 发布频率、延迟、抖动、吞吐、QoS |
| 异常 | 缺失值、过期值、错误码、超时与重试规则 |
| 演进 | 接口版本、兼容策略、弃用周期 |

### 3.3 控制权和硬件接口契约

- **控制权**：定义自主、遥操作、标定、维护和急停模式的优先级，以及使能、接管、取消、复位的权限与条件。
- **机械接口**：安装面、坐标基准、尺寸公差、质量和重心边界。
- **电气接口**：连接器 pin、电压等级、峰值电流、上电顺序、接地和急停链。
- **计算与热接口**：功耗上限、散热条件、CPU/GPU 资源边界。

关键交接物包括系统架构图、接口控制文档 (ICD)、状态机、TF 树、网络拓扑、线束图、ROS 接口表和兼容性矩阵。

## 四、全系统预算与余量

### 4.1 端到端实时预算

```text
总延迟 = 采集 + 传输 + 排队 + 计算 + 下发 + 执行
```

除了平均延迟，还应关注：

- 截止期限和最坏执行时间 (WCET)。
- P95/P99/最大延迟和控制周期抖动。
- 数据年龄、deadline miss 与过期目标比例。
- 多速率模块之间的缓存、插值、采样保持和背压策略。

### 4.2 通信与计算资源预算

- **通信**：按消息大小、平均/峰值频率、序列化开销估算带宽，并预留突发流量。
- **计算**：统计 CPU/GPU/NPU、实时核、线程优先级、显存、内存和存储写入余量。
- **过载**：优先保留估计、控制与安全链；按等级降低视觉频率、暂停上传或关闭非关键 AI 服务。
- **实时环**：避免动态内存分配、阻塞 I/O、锁竞争、优先级反转和非确定性日志写入。

### 4.3 物理与成本预算

质量、重心、惯量、功率、峰值电流、续航、热设计、结构强度、线束空间和成本都应从整机向子系统分配。评审时区分：

- 目标值与设计值。
- 典型工况与最坏工况。
- 仿真值与实测值。
- 已使用余量与剩余余量。

## 五、风险、安全、可靠性与降级

### 5.1 风险分析

可根据项目使用 FMEA/FMECA、故障树 (FTA)、STPA 或 HARA，识别：

- 危险事件和触发条件。
- 单点故障与共因失效。
- 严重度、发生度和可探测度。
- 预防、检测、隔离和缓解措施。
- 措施对应的验证用例和残余风险。

### 5.2 故障检测、隔离与恢复 (FDIR)

```text
Fault Detection → Fault Isolation → Recovery / Degradation
```

传感器越界、节点超时、总线掉站、模型异常、过温、欠压和通信中断都应映射到明确错误码、责任模块和响应动作。

### 5.3 分级降级

一种通用思路是：

```text
正常 → 能力受限 → 受控停止 → 阻尼/抱闸 → 切断动力
```

具体顺序不能机械套用：双足机器人掉线时可能需要短时间保持平衡，而固定机械臂可能更适合立即停止。设计时需要区分：

- **Fail-safe**：故障后进入低风险静止状态。
- **Fail-operational**：故障后仍维持有限关键能力，例如保持平衡或撤离危险区。

急停复位不等于恢复运动。系统必须定义自动恢复、人工确认和禁止自动重启的边界。

### 5.4 冗余不是简单复制

关键传感器、通信、电源或计算可以冗余，但还需处理投票、故障隔离、共因失效、状态同步和切换瞬态，否则双份模块可能产生双份错误。

## 六、可观测性、诊断与故障复盘

### 6.1 三类可观测信号

- **Logs**：结构化事件、错误码和上下文。
- **Metrics**：频率、延迟、资源、温度、电压和成功率。
- **Traces**：一次任务跨节点、跨主机的事件链。

这些信号应统一时间戳，并携带机器人 ID、任务 ID、软件版本、配置哈希和严重等级。

### 6.2 健康监测与黑匣子

持续监测节点心跳、Topic 频率与延迟、CPU/GPU/温度、内存、磁盘、网络丢包、现场总线、电池和关节错误。

黑匣子可使用环形缓冲保存故障前后的关键传感、估计、目标、控制模式、限幅结果与错误码；事件触发时固化 rosbag、日志和配置快照，避免问题发生后才发现没有证据。

### 6.3 告警与复盘闭环

- 告警分为提示、警告、故障和紧急等级，并进行去抖、抑制和聚合。
- 复盘按“时间线 → 首个异常 → 根因 → 临时处置 → 永久修复 → 回归用例”推进。
- 最后的报错通常只是结果，不一定是首因。

## 七、配置、版本、变更与发布

### 7.1 需要统一管理的版本对象

- 源码、依赖、固件和 Docker 镜像。
- URDF/MJCF、标定、控制参数和地图。
- AI 模型、数据集、归一化参数和关节顺序。
- 机械/电气硬件版本与 BOM。

### 7.2 兼容性矩阵与启动校验

维护“机型/硬件 × 固件 × ROS 包 × 模型 × 参数”的已验证组合。启动时至少校验：

- 机型、关节数量与关节名称。
- 接口版本和消息字段。
- URDF、模型、标定和配置哈希。
- 固件与上位软件兼容范围。

### 7.3 配置分层与变更控制

默认值、机型配置、单机标定、现场配置和临时覆盖应分开。参数注明单位、范围、来源、修改人和生效方式。

高风险控制或安全参数的变更需要影响分析、评审和双人复核，并关联需求、问题单与测试证据。

### 7.4 发布与回滚

发布制品应不可变、带版本和校验和。采用灰度部署、启动前校验、健康检查和明确回滚路径；参数或数据格式迁移需要考虑向前与向后兼容。

## 八、验证与确认 (V&V)

### 8.1 测试阶梯

```text
静态检查/单元测试
→ 模块测试
→ MIL/SIL
→ HIL
→ 台架与子系统
→ 整机仿真
→ 受保护真机
→ 目标场景验收
```

- **MIL**：Model-in-the-Loop，验证模型和算法逻辑。
- **SIL**：Software-in-the-Loop，验证真实软件与仿真环境的接口。
- **HIL**：Hardware-in-the-Loop，引入控制器或真实硬件验证时序和接口。

### 8.2 需求驱动与鲁棒性测试

每条关键需求至少对应一个测试方法和通过阈值，并保存环境、输入、版本、原始数据和报告。

鲁棒性测试应覆盖边界值、随机/属性测试、故障注入、网络延迟与丢包、传感器失真、资源压力、长稳、断电恢复和重复启停。

### 8.3 安全路径独立验证

急停、限位、看门狗、断连和降级路径需要绕过正常业务链单独测试，并确认业务线程阻塞、资源耗尽或网络异常不会同时阻塞安全响应。

修复真机问题时，先建立最小复现，再沉淀为自动回归。仿真通过不能替代台架和真机场景验证。

## 九、网络安全与供应链安全

### 9.1 威胁建模与最小权限

识别资产、信任边界、攻击面和滥用场景，重点保护运动使能、远程维护、OTA、模型/参数和采集数据。

- 普通业务节点不使用 root。
- 控制网、办公网和外网分区。
- 服务、端口、DDS Domain 与访问控制按需开放。
- 网络攻击导致的延迟、伪造指令或失联进入功能安全降级链。

### 9.2 身份、密钥与可信更新

- 设备身份和双向认证。
- 密钥轮换与安全存储。
- 禁止在源码、镜像、launch 和日志中硬编码凭据。
- 安全启动、签名固件/镜像、完整性校验和回滚保护。
- 维护 SBOM，跟踪第三方依赖和供应链漏洞。

## 十、运维、维护性与现场闭环

### 10.1 可维护设计与运维基线

模块化更换、连接器防错、测试点、诊断口、校准工装和维修手册应在设计阶段考虑。交付时至少具备：

- 部署、启动、停止和安全操作 SOP。
- 备份恢复、日志留存与远程诊断方法。
- 备件、耗材和定期点检计划。
- 版本清单和现场配置基线。

### 10.2 可靠性指标

按场景跟踪任务成功率、可用率、故障间隔、平均修复时间 (MTTR)、降级次数、安全触发原因和人工接管频率。指标必须与 ODD 和任务难度一起解释。

### 10.3 现场数据反馈

现场故障和困难样本经过脱敏、筛选与版本标注后，回流到仿真、测试集和训练集。修复或重训后重新完成回归与场景验收，再进入发布流程。

设备转移或退役前，需要清理密钥、账号、用户数据、地图、日志和存储介质。

## 十一、评审节点与核心交付物

### 11.1 常见评审节点

| 评审 | 关注点 |
|------|--------|
| SRR | 需求、ODD、KPI 和验收方法是否明确 |
| PDR | 总体架构、关键接口、预算和主要风险是否闭合 |
| CDR | 详细设计是否可制造、可实现、可测试 |
| TRR | 测试环境、用例、仪器、安全措施和版本是否就绪 |
| 发布评审 | 已知问题、风险接受、兼容性、回滚和运维是否就绪 |

### 11.2 最小系统文档集

- 需求基线与 ODD。
- 系统架构说明和 ICD。
- 实时、通信、算力、功耗、质量和热预算。
- 风险清单、FMEA/FTA 与安全状态机。
- V&V 追溯矩阵和测试报告。
- 兼容性矩阵、版本清单和发布说明。
- 部署、运维、维修和应急 SOP。

## 十二、项目落地检查表

### 架构冻结前

- [ ] ODD、关键 KPI 和失败边界已定义。
- [ ] 模块职责、控制权和接口契约已评审。
- [ ] 实时、通信、算力和物理预算有余量。
- [ ] 高风险故障有检测、降级和验证方案。

### 集成前

- [ ] 硬件、固件、URDF、标定、模型和参数版本可追溯。
- [ ] 启动时执行兼容性和配置校验。
- [ ] 日志、指标、黑匣子和错误码可用。
- [ ] MIL/SIL/HIL 或台架测试已覆盖关键接口。

### 真机与发布前

- [ ] 急停、限位、看门狗、断连和过载路径已独立验证。
- [ ] 关键场景、边界场景、长稳和故障注入达到验收阈值。
- [ ] 发布制品可回滚，已知问题和残余风险已记录。
- [ ] 运维、备份恢复、远程诊断和应急 SOP 已交付。
