# 机器人安全工程：从风险分析到验证闭环

> **定位**：安全不是一份操作注意事项，也不是“加急停和限位”即可完成。安全工程需要贯穿需求、架构、设计、集成、验证、发布和运维，并用风险分析与测试证据证明风险已被合理降低。
>
> 本文讨论通用工程方法，不替代适用法律法规、认证标准、制造商说明书或组织安全制度。具体安全等级、性能等级、停止距离和测试阈值必须由项目风险评估确定。
>
> 相关入口：[全链路思维导图](../robot_system.md) · [真机调试 SOP](./safety_sop.md) · [系统工程](./systems_engineering.md) · [硬件与整机工程](./hardware_system_engineering.md) · [系统集成](./robot_system_integration.md)

## 一、安全工程的对象与边界

### 1.1 Safety 与 Security

- **功能安全/机械安全 (Safety)**：防止随机硬件故障、系统失控、机械运动、能量释放和人为误操作造成伤害。
- **网络与信息安全 (Security)**：防止未授权访问、伪造指令、恶意更新和数据泄露。
- 两者必须协同：攻击导致的失联、延迟或伪造运动指令，最终仍需进入安全检测和降级链。

### 1.2 安全生命周期

```text
场景与人员分析
→ 危险识别和风险评估
→ 安全目标与安全需求
→ 安全架构和保护措施
→ 实现、独立验证与确认
→ 发布、运行监测和事件闭环
→ 变更影响分析与再验证
```

安全需求必须可追溯到危险场景，并有对应的实现和测试证据。

## 二、场景、人员与危险识别

### 2.1 先定义使用场景

风险评估至少说明：

- 机器人形态、质量、速度、负载和可达空间。
- 正常生产、调试、标定、运输、维护、充电和救援状态。
- 操作者、维护人员、普通公众、儿童等可能接触者。
- 室内/室外、地面、光照、网络、温湿度和电磁环境。
- 合理可预见的误用，例如绕过门禁、错误模式切换或站入运动区。

### 2.2 典型危险源

| 类别 | 示例 |
|------|------|
| 机械 | 挤压、剪切、夹点、冲击、卷入、跌倒、抛射、末端工具 |
| 电气 | 触电、短路、过流、绝缘失效、意外上电 |
| 热与火灾 | 电机/驱动过温、电池热失控、热表面 |
| 控制 | 错误目标、失控运动、模式混乱、过期指令、限幅失效 |
| 感知 | 漏检、误检、遮挡、定位漂移、时间/坐标错误 |
| 通信 | 丢包、延迟、链路中断、错误节点接管 |
| 软件/AI | 状态机缺陷、模型分布外输入、版本错配、资源耗尽 |
| 人因 | 误操作、告警理解错误、维护绕过、疲劳和培训不足 |
| 环境 | 地面湿滑、坡度、强光、粉尘、雨水、电磁干扰 |

不能只分析正常自主运行；调试、手动搬运、故障恢复和维护往往风险更高。

## 三、风险评估方法

### 3.1 风险评估基本步骤

1. 识别危险源、危险状态和可能伤害。
2. 评估严重度、暴露频率、发生可能性与可避免性。
3. 制定风险降低措施并分配安全需求。
4. 评估残余风险并确定是否需要进一步措施。
5. 用分析、检查和测试形成证据。

风险参数和接受准则应采用项目适用的方法与标准，不能把某个行业的打分表直接套用到所有机器人。

### 3.2 常用分析工具

- **FMEA/FMECA**：从部件或功能失效出发，分析局部影响、系统影响和检测措施。
- **FTA**：从顶层危险事件向下分解导致事件的故障组合。
- **STPA**：分析复杂控制系统中的不安全控制行为、约束和反馈缺失。
- **HARA/任务风险分析**：按运行场景评价危险和风险等级。

这些方法互补而非互相替代。分析结果至少应记录危险 ID、触发条件、后果、安全要求、实现措施、验证方法和残余风险。

## 四、安全要求与分层防护

### 4.1 风险降低优先顺序

安全设计通常遵循：

1. **本质安全设计**：降低质量、速度、力、尖角、夹点和储能。
2. **工程防护**：围栏、门锁、机械限位、制动、急停、安全控制器。
3. **信息与管理措施**：告警、说明书、培训、SOP 和个人防护。

SOP 是最后一层管理控制，不能替代本质安全设计和工程防护。

### 4.2 防护层次

```text
任务/规划约束
→ 安全监控与控制权仲裁
→ 位置/速度/力矩/功率限制
→ 驱动器保护与安全停机
→ 接触器/制动/急停
→ 机械限位、外壳、围栏和物理隔离
```

多层防护需要尽可能避免共因失效。例如业务进程、软件限位和看门狗若全部运行在同一进程中，就可能被一次崩溃同时破坏。

### 4.3 安全需求应可验证

安全需求应明确：

- 监测对象、检测阈值和有效范围。
- 检测时间、响应时间和最大停止时间/距离。
- 故障后的目标状态。
- 自动恢复、人工复位和重新使能条件。
- 诊断覆盖、测试周期和证据保存方式。

## 五、安全状态、控制权与停止策略

### 5.1 安全状态机

一种通用状态划分是：

```text
断能/维护
→ 上电未使能
→ 已使能待机
→ 自动或遥操作运行
→ 能力受限
→ 受控停止
→ 紧急停止/故障锁定
```

项目需要定义每个状态允许的动作、进入/退出条件、控制权所有者和复位权限。

### 5.2 停止不是单一动作

不同危险和机器人形态需要不同响应：

- **受控停止**：在控制保持有效时减速并进入稳定状态。
- **阻尼/柔顺状态**：降低刚度和冲击，但要评估重力下落风险。
- **保持/制动**：固定机械臂可防止负载下落，但人形全身锁死未必总是安全。
- **切断动力**：适合需要消除驱动力的场景，但可能引发自由下落。
- **维持关键能力**：双足平台链路故障时，短时间保持平衡后再停机可能比立刻断能更安全。

因此不能把“掉线后一律锁死”或“一律断电”作为通用安全策略。

### 5.3 控制权仲裁

自主、遥操作、调试、标定、维护和急停之间必须有唯一、明确的优先级：

- 安全链可否决运动，业务层不能绕过。
- 接管请求需要握手、状态确认和超时处理。
- 模式切换采用限幅、插值或渐进接管，避免指令阶跃。
- 复位故障不等于恢复任务，重新运动前应再次确认环境和状态。

## 六、硬件安全设计

### 6.1 急停与动力切断

- 急停是补充保护措施，不替代防护和正常停止功能。
- 急停回路应独立于普通业务软件，并考虑触点粘连、断线和复位检测。
- 动力电与逻辑电是否分离、急停后是否保留日志能力，应根据风险和架构确定。
- 复位急停只能允许重新使能，不能直接触发运动。

### 6.2 制动、机械限位与防坠

- 抱闸选型需考虑静态保持、动态制动、热容量、磨损和释放检测。
- 机械限位承受的软件失效后残余能量必须经过校核。
- 垂直轴、重载机械臂和人形吊装需要独立防坠措施。
- 外壳、圆角、缓冲和易碎/吸能结构用于降低碰撞后果。

### 6.3 电池、电气和热安全

- 过流、短路、过压、欠压、过温、绝缘和接地故障需要分级保护。
- 电池关注机械固定、热失控传播、泄压、充电和运输。
- 高温表面、风扇失效和散热堵塞进入安全监测与降额策略。
- 维护时采用断能、验电和防止意外重启措施。

## 七、软件、通信与 AI 安全

### 7.1 软件安全机制

- 关节位置、速度、力矩、电流、功率和温度限值。
- 指令新鲜度、范围、变化率和坐标系检查。
- 节点心跳、控制周期、数据频率和 deadline 监测。
- 异常状态机、错误码、事件记录和锁存故障。
- 安全相关配置采用范围校验、版本校验和受控变更。

### 7.2 看门狗与故障隔离

看门狗必须定义“监测谁、超时多久、执行什么、由谁执行”。软件看门狗、独立进程、驱动器超时和硬件看门狗可构成不同层级，避免被同一故障同时击穿。

### 7.3 通信和网络安全

- 控制目标带时间戳和有效期，过期后丢弃而非继续执行。
- 链路中断、丢包、乱序和重连需要明确降级状态。
- 控制网与外网分区，采用身份认证、最小权限和访问控制。
- 更新包、固件、模型和配置采用签名与完整性校验。

### 7.4 AI/学习系统的额外约束

- 明确训练分布、运行设计域和分布外输入检测策略。
- 对策略输出进行范围、变化率、能量和可行性约束。
- 模型、观测维度、归一化、关节顺序和 URDF 版本启动时校验。
- 学习策略不能绕过独立安全监控和低层驱动保护。
- 仿真成功不能替代受保护真机测试和故障注入。

## 八、人机交互、协作与人因

- 操作者应能看懂当前模式、控制权、运动使能和故障状态。
- 告警要区分提示、警告、故障和紧急，避免告警风暴。
- 启动和模式切换提供声光或界面提示，并留出人员撤离时间。
- 遥操作考虑网络延迟、视野盲区、尺度映射和误触发。
- 维护界面不应默认拥有运动权限；高风险操作可采用双人确认。
- 培训、SOP 和禁区应与真实危险分析一致，而不是固定模板。

真机调试中的龙门架、双人操作、低速空载和起立接管步骤见 [真机安全 SOP](./safety_sop.md)。

## 九、安全验证与确认

### 9.1 分层验证

```text
安全需求评审
→ 单元/静态分析
→ MIL/SIL
→ HIL 与驱动台架
→ 故障注入
→ 受保护整机
→ 场景与残余风险确认
```

### 9.2 必测项目

- 急停、保护停止、限位、制动和重新使能。
- 传感器断开、卡死、漂移、越界和时间戳异常。
- 节点崩溃、CPU/GPU 过载、内存耗尽和存储写满。
- 网络延迟、丢包、断连、乱序和重复消息。
- 总线掉站、驱动故障、过温、欠压和电池异常。
- 模型/配置不匹配、错误坐标系和过期目标。
- 单一保护措施失效时，剩余防护是否仍能降低风险。

### 9.3 测试证据

记录机器人和硬件版本、软件/模型/配置哈希、测试环境、输入故障、期望响应、实测响应时间、停止距离、日志和视频。未通过项必须关联整改和回归测试。

安全路径应尽可能独立验证，不能只通过正常业务流程间接测试。

## 十、运行、事件与变更管理

### 10.1 上线与运行

- 发布前确认残余风险、适用场景、已知限制和应急措施。
- 监测安全触发、人工接管、保护停止、故障频率和恢复时间。
- 安全日志和黑匣子保存故障前后的观测、目标、模式和保护动作。
- 定期测试急停、制动、门锁、限位、告警和备份恢复。

### 10.2 事件处置

```text
保护现场与人员
→ 停止复现高风险动作
→ 固化日志/rosbag/配置/版本
→ 建立事件时间线
→ 根因与系统性原因分析
→ 整改、回归和风险评估更新
```

安全事件不能只以“操作员失误”结案，还需要分析界面、流程、权限、提示和设计是否允许该错误直接导致危险。

### 10.3 变更影响分析

硬件、固件、URDF、控制参数、AI 模型、网络拓扑、速度和负载的变化都可能使原安全结论失效。变更前需要识别受影响的危险、安全要求和测试，并完成相应再验证。

## 十一、安全交付物

- 安全计划、适用标准和职责分工。
- 场景/人员/合理可预见误用清单。
- 危险日志、风险评估、FMEA/FTA/STPA 结果。
- 安全需求规范和需求追溯矩阵。
- 安全架构、状态机、停止/降级策略和接口定义。
- 安全相关硬件/软件设计与配置基线。
- 验证计划、故障注入记录和测试报告。
- 残余风险、用户说明、维护要求和真机 SOP。
- 事件响应、变更控制和周期性检查记录。

## 十二、落地检查表

### 设计阶段

- [ ] 已覆盖正常、调试、维护、运输、充电和故障恢复场景。
- [ ] 每个主要危险都有安全目标、实现措施和验证方法。
- [ ] 已优先采用本质安全设计和工程防护，而不是只依赖 SOP。
- [ ] 安全链与普通业务链之间的独立性和共因失效已分析。

### 集成与真机阶段

- [ ] 控制权、模式切换、指令有效期和复位条件明确。
- [ ] 急停、限位、看门狗、制动、断连和过载均已故障注入。
- [ ] 每种故障的目标安全状态和实测响应符合项目要求。
- [ ] 现场隔离、龙门架、人员站位和应急措施与风险评估一致。

### 发布与运维阶段

- [ ] 安全配置、硬件、固件、模型和测试证据版本一致。
- [ ] 残余风险、使用边界、维护周期和应急 SOP 已交付。
- [ ] 安全事件可通过日志和黑匣子复盘。
- [ ] 任何影响运动、能量或防护的变更都会触发安全影响分析。
